# 1. A tour of the demo

**Goal:** know Crown Match's layout well enough to find any piece of it, before reading the code line by line.

**What you'll learn**

- How to load the demo and find its scripts in the editor.
- The three scenes and their one-state Code programs.
- How one JavaScript file becomes three programs (a shared library plus per-scene sections).
- The scene's naming conventions: the node Ids the script depends on.
- The big design decisions: a fixed node pool, a data model in `ctx.globals`, a phase machine in code.

## Play it first

<ToastyDemo game="/games/crown-match.teab" height={560} caption="Crown Match. Drag a gem onto a neighbour (or tap one, then the other) to swap. Match 3 or more." />

Things to try while playing, because you'll meet each of them in the code:

- Match **4 in a row**: you get a **Rocket** (a gem with a stripe) that clears a whole row or column.
- Match an **L or T** shape: you get **TNT** (a ring), which clears a 5 × 5 area.
- Match **5 in a row**: you get a **Light Ball**, a spinning, colour-cycling star. Swap it with a gem to clear that colour.
- Swap **two specials** together: they combine.
- Wait 5 seconds without moving: two gems start wiggling as a hint.
- Finish a level, then go back to the map: your stars are saved, even after a page reload.

## Open it in the editor

1. **+** → **Demos** → **Crown Match (match-3)**. Three new scenes are added: `Crown Match Home`, `Crown Match Levels` and `Crown Match Game`. Your own scenes are left alone.
2. Switch to **Code** mode. Under **Scene scripts** in the explorer, each scene lists its one state: `Home`, `Levels` and `Game`. Click one to read it.
3. To run it, open `Crown Match Home` in the **Scene** dropdown and press **Playground**.

<Shot id="match3-code-mode" caption="Code mode with Crown Match loaded: Scene scripts lists Home, Levels and Game; the Game script is open." />

## How the scenes fit together

| Scene | State | What it does | Leaves with |
|---|---|---|---|
| Crown Match Home | `Home` | Title, bobbing crown, drifting gems, PLAY and LEVEL MAP buttons. | `go('Crown Match Game')` or `go('Crown Match Levels')` |
| Crown Match Levels | `Levels` | A winding map of 20 levels with saved stars, locks and the next level pulsing. | `go('Crown Match Game')` or back home |
| Crown Match Game | `Game` | The 8 × 8 board, goals, moves, score, specials, result panel. | `go('Crown Match Levels')` |

Each scene has a state machine with exactly one Programmable State. There are no transitions: the whole game flow is scene switches with `ctx.loadScene`, and the in-game flow (swapping, clearing, falling) is a little state machine written in code, as you'll see in lesson 5.

## One file, three programs

The demo's source is one JavaScript file, `demo_match3.js`, shaped like this:

```js
// ... shared library: constants, helpers, save data, level generator ...

//@program Home
// ... the Home scene's code ...

//@program Levels
// ... the Levels scene's code ...

//@program Game
// ... the Game scene's code ...
```

When the demo is built, the engine splits the file at each `//@program` marker and gives each scene **the library plus its own section** (with a `// ---- Home ----` style header between them). So every scene's program starts with the same ~90 lines of shared code. That's why, when you open the `Game` script in Code mode, you see the save-data and level-generator code at the top.

:::tip Doing this in your own project
You can get the same effect without a build step: put shared helpers in a project file and run per-scene code from each state. Or do what the platformer course does: one file for every scene, branching on `ctx.scene`.
:::

## The node Ids the script relies on

Crown Match is built entirely from vector shapes, no images. The script finds every node by **Id** (`getCompByID`). The important ones in the Game scene:

| Id pattern | Count | What it is |
|---|---|---|
| `board` | 1 | The board's well: a Shape with **clip children** on, so gems sliding in from above are masked to it. |
| `cell0` … `cell63` | 64 | The checkered background squares. Hidden where a level has holes. |
| `frost0` … `frost63` | 64 | Frost overlays (hidden until a level uses them). |
| `gem0` … `gem63` | 64 | **The gem pool.** Every gem you ever see is one of these 64 nodes, re-shaped and re-coloured. |
| `gem<i>H`, `gem<i>V`, `gem<i>R` | 64 each | Children of each gem: horizontal stripe, vertical stripe, TNT ring markers. |
| `tpl0` … `tpl6` | 7 | Hidden template shapes: the six gem outlines plus the Light Ball. The script copies their paths. |
| `sel` | 1 | The white selection ring. |
| `pop0` … `pop6`, `blast`, `confetti` | 9 | Particle Systems parked off-screen until needed. |
| `float0` … `float5` | 6 | Floating score texts ("+180"), reused round-robin. |
| `movesText`, `scoreText`, `goalText0..2`, `scoreFill`, `barStar0..2`, … | | The heads-up display. |
| `dim`, `panel`, `resultTitle`, `resultStar0..2`, `nextBtn`, `map2Btn`, … | | The result overlay, hidden until a level ends. |

Buttons are pairs: a plate Shape `<name>Btn` and a Text `<name>Label` (`playBtn` / `playLabel`).

## Three design decisions

Keep these in mind; the rest of the course is details.

1. **A fixed pool of 64 gem nodes.** Spawning and deleting nodes during play is possible (`ctx.spawn`, `spawnClone`), but a board never shows more than 64 gems, so the scene simply owns 64 and the script recycles them. A cleared gem's node goes back on a free list and comes back as the next gem dropping in.
2. **The real game is data.** The board lives in `ctx.globals` as a grid of plain objects (`{ t, sp, r, c, x, y, … }`). Matching, gravity and specials only touch this data. A separate "visuals" pass at the end of each frame copies positions, scales and looks onto the pool nodes.
3. **A phase machine in code.** One variable, `g.phase`, says what the board is doing: `intro`, `idle`, `swap`, `unswap`, `clear`, `fall`, `settle`, `won`, `lost`. Each frame does a little work for the current phase and maybe moves to the next. Animations are timers plus maths, not keyframes.

## Check your work

- You can load the demo, find the `Game` script in Code mode, and play from Home.
- You can point at any gem on the board in Playground and name the kind of node it is (`gem<i>`, from a pool of 64).
- You can explain why the Game script starts with level-generator code that has nothing to do with the board's rendering (the shared library is prepended to every scene).
