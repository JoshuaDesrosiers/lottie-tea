# 1. Plan the button

**Goal:** know exactly what you're building and agree the "contract" between the animation and the web page before you touch the editor.

**What you'll learn**

- What the finished like button does, from the user's and the page's point of view.
- The three ways a Toasty scene talks to a page: **data** (Properties), **state machine states**, and **events**.
- Why you design that contract first.

## The finished button

Click the card to start it, then click the heart a few times.

<ToastyDemo game="/games/like-button.teab" height={320} caption="The finished like button. Click the heart to like and unlike." />

When you click the heart:

1. It flips between grey (**Idle**) and red (**Liked**), with a springy pop and a burst of sparks when you like it.
2. The count under it goes up or down by one.
3. The scene sends the page an event called `like` with `{ liked, count }`.

The page, meanwhile, can tell the button "this post already has 1,204 likes and this user liked it" by setting two values, and the button updates instantly.

## The contract

Any embedded scene is easiest to work with when you write its surface down first: what goes in, what comes out. Here is the like button's:

| Kind | Name | Type | Direction | Meaning |
|---|---|---|---|---|
| Property | `count` | Number, default `128` | page → scene, scene → page | The number shown under the heart. |
| Property | `liked` | Bool, default `false` | page → scene, scene → page | Whether the current user has liked it. |
| State machine input | `burst` | Trigger | internal | Flips the heart between its two states. |
| States | `Idle`, `Liked` | (base layer) | scene → page | Which look the heart has right now. |
| Event | `like` | `{ liked: boolean, count: number }` | scene → page | Sent once per click. |

Three channels carry everything:

- **Properties** are values. The page writes them with `player.set('count', 1204)`, or in React with `data={{ count: 1204 }}`. A scene Property with the same name takes the value, and anything bound to it (like the count label) updates on the next frame. See [Data binding](../../embedding/data-binding.mdx).
- **States** are moments. Every time the state machine enters a new state, the page hears about it (`onStateChange`). That lets an animation carry meaning: "the heart is now in `Liked`".
- **Events** are messages. A script calls `ctx.emit('like', payload)` and the page's `onEvent` handler receives it. See [Listening to the game](../../embedding/listening.mdx).

:::tip Values versus moments
A click is a *moment*, so it travels as an event. Whether the post is liked is a *value*, so it lives in a Property. Keeping that split clean is what makes the React side simple later: the page never has to "replay" clicks, it only ever sets values.
:::

## Where the logic lives

Two places could own the click logic: the page or the scene. In this course the **scene** owns the immediate reaction (flip the heart, change the count, play the pop), so the button feels instant even before your server answers. The **page** owns the truth: it saves the like to the server and, when the server answers, sets the real count back into the scene. Lesson 5 builds that "optimistic UI" loop.

## Check your work

- You clicked the finished heart and saw Idle and Liked.
- You can say, without looking, which channel carries the like count (a Property), which carries a click (an event), and which tells you the heart is red (a state).
