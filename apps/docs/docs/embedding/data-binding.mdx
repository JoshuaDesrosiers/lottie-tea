# Sending data in

Your page has five ways to steer a running game. Choosing the right one makes the game simpler to build and the page simpler to write.

| You want to… | Use | React |
|---|---|---|
| Hand the game a **value** (difficulty, player name, colour, a flag) | `player.set(name, value)` / `setData({...})` | `data={{ ... }}` |
| Put the **state machine** in a mode (paused, level, tab) | `player.setInput(name, value)` | `inputs={{ ... }}` |
| Make something **happen now** in the state machine | `player.fire(trigger)` | `ref.current.fire(trigger)` |
| Go to another **scene** | `player.loadScene(name)` | `scene="..."` |
| Run **game code** and maybe get a result back | `player.call(name, arg)` | `ref.current.call(name, arg)` |

## Data: `set`, `setData`, `data`

Data are **values**. Each one you send goes to up to two places in the game:

1. **`ctx.data` in the game's scripts**: `ctx.data.speed`. Any key works; it doesn't need to be declared anywhere.
2. **The scene Property with the same name**, if the scene has one. Properties are named values you add to a scene in the editor (click empty canvas, then **Properties** in the Inspector). Anything bound to a Property updates by itself: a Text node showing it, a fill colour, visibility, any component field (see [Properties and bindings](../editor/properties-and-bindings.mdx)). **No script is needed.**

```js
player.set('speed', 1.5)
player.setData({ speed: 1.5, playerName: 'Maya Chen' })
```

```tsx
<An1Player game="/an1mbyt3/game.teab" data={{ speed, playerName }} />
```

[Toast Catch](../games/toast-catch.mdx) reads `ctx.data.speed` every frame to scale how fast the toast falls. Pick a difficulty, mid-round if you like:

```jsx live
function Difficulty() {
  const levels = { Relaxed: 0.7, Normal: 1, Hectic: 1.6 }
  const [level, setLevel] = React.useState('Normal')
  return (
    <div>
      <ToastyPlayer game="/games/toast-catch.teab" data={{ speed: levels[level] }} style={{ height: 300 }} />
      <div role="radiogroup" style={{ display: 'flex', gap: 8, marginTop: 8 }}>
        {Object.keys(levels).map((name) => (
          <button key={name} role="radio" aria-checked={name === level} disabled={name === level}
            onClick={() => setLevel(name)}>
            {name}
          </button>
        ))}
      </div>
    </div>
  )
}
```

On the game side that is one line, with a default so the game also works in the editor, where `ctx.data` is empty:

```js title="in the game"
const speed = (Number(ctx.data.speed) || 1) * (1 + ctx.props.score / 40)
```

### Types and conversion

`ctx.data` keeps exactly what you sent. When a key also matches a scene Property, the value written into the Property is converted to the Property's type, so you don't have to be careful about strings versus numbers:

| Property type | Accepts | Becomes |
|---|---|---|
| Number | a number, or anything `Number(...)` can read (`'42'`) | that number; `0` if it isn't a finite number |
| Bool | `true`, `1`, `'true'`, `'1'`, `'on'` | `true`; anything else is `false` |
| Text | anything | `String(value)`; `null` and `undefined` become `''` |
| Color | `'#rrggbb'` or `'rrggbb'`, or `[r, g, b]` / `[r, g, b, a]` with channels from 0 to 1 | `[r, g, b, a]`; anything else becomes white |

Short colours like `'#fff'` and CSS names like `'red'` are **not** understood (they turn white). Convert them to six-digit hex first.

### When it takes effect

- `set` is **applied at the next frame**. Calling it many times between frames just keeps the latest value, so it is cheap enough to call on every keystroke, every scroll event, every poll.
- Data are **kept across scene switches**. When the game enters a scene, all the data you've sent are applied to that scene's Properties. (Properties themselves reset to their defaults on every scene switch; your data are then re-applied on top.)
- `player.get(name)` returns the scene Property's current value (which may have been changed by the game since), or, if there is no such Property, the last value you `set`.

### Values, not pulses

Sending the same value again changes nothing: the game sees the latest value every frame. That makes data the wrong tool for "do this now". For one-off actions use a [function call](#calling-game-code-call) or a [trigger](#triggers-fire).

If a game reads a data value as a one-shot flag (for example "when `ctx.data.celebrate` is true, celebrate"), send `false` before sending `true` again.

### Properties the game writes

Some Properties belong to the game: Toast Catch's `score` and `lives` change on every catch. Read those with [`prop` events](./listening.mdx#property-changes) rather than sending them.

If you do send one, here is exactly what happens:

- **Each frame, only the keys you sent since the last frame are written.** `player.set('lives', 5)` writes `lives` once. A later `player.set('speed', 2)` writes only `speed`, so whatever the game has done to `lives` in between stands.
- **After a scene switch, every value you have sent is applied again** to the new scene's Properties, including `lives: 5`.
- Sending the same key again writes it again, replacing the game's value at that moment.

So a one-off `set` is a safe way to nudge a game value (a "bonus life" button, say), but the game and the page shouldn't both own the same Property. Keep regular page data to keys the game only reads, like `speed`.

### Data from your server

The page fetches, the game shows. Don't fetch from inside the game; fetch in your page and `set` the result:

```js
const player = await createPlayer(box, { game: '/an1mbyt3/game.teab' })

// A difficulty your team tunes without re-exporting the game.
const config = await (await fetch('/api/game-config')).json()   // { speed: 1.2, playerName: 'Maya Chen' }
player.setData(config)
```

```tsx
const { data: config } = useQuery({ queryKey: ['game-config'], queryFn: fetchConfig })

<An1Player game="/an1mbyt3/game.teab" data={{ speed: config?.speed ?? 1 }} style={{ height: 360 }} />
```

Keys without a matching Property only reach `ctx.data`, so sending a whole response is harmless. Notice what the page does *not* do: it never touches how the game draws anything. It sends `speed: 1.2` and the game decides what that means.

## Inputs: `setInput`, `inputs`

State machine inputs pick what the [state machine](../editor/state-machines.mdx) does. The page can set any input of the current scene's active state machine:

```js
player.setInput('paused', true)        // Bool
player.setInput('difficulty', 2)       // Number
player.setInput('tab', 'settings')     // Enum (by option name)
player.setInput('restart', true)       // Trigger: fires when the value is truthy
```

```tsx
<An1Player game="/an1mbyt3/game.teab" inputs={{ paused, difficulty: 2 }} />
```

Values are converted to the input's kind (`Boolean(value)`, `Number(value)`, `String(value)`). A name the state machine doesn't have logs `the scene's state machine has no input "…"` in the browser console and does nothing.

Toast Catch and Hop run their logic in a script, so their state machines have no inputs. Inputs shine in state-machine-driven scenes: a heart that is liked or not, a menu icon that is open or closed. On a website those are usually UI animation, which [Toasty Lite](../runtimes/lite.mdx) plays with the same `setInput` API and no one-per-page limit; see the [like button](../use-cases/like-button.mdx) for a complete example.

### Data or input?

Both are values. The difference is who reacts:

- An **input** is read by the **state machine's transitions** ("go from Playing to Paused when `paused` is true"). Use it when the value should change which state is active.
- A **data value or Property** is read by **bindings and scripts** ("this label shows `playerName`", "the toast falls at `speed`"). Use it when the value should be displayed or used in code.

A game can offer both for the same idea, for example a `paused` input that moves the state machine and a `paused` Property that a "Paused" label is bound to.

## Triggers: `fire`

A Trigger input is a one-shot: firing it lets a transition happen once. Use it for moments.

```js
player.fire('restart')
```

In React, fire through the ref, because a trigger is an action, not state:

```tsx
<button onClick={() => ref.current?.fire('restart')}>Play again</button>
```

You *can* put a trigger in `inputs`, but it only fires when its value changes to truthy (`{ restart: count }` fires each time `count` changes to a new non-zero number, `{ restart: true }` fires once). `fire` is clearer.

## Scenes: `loadScene`, `scene`

```js
player.loadScene('Level 2')
```

```tsx
<An1Player game="/an1mbyt3/game.teab" scene={level === 2 ? 'Level 2' : 'Level 1'} />
```

The switch happens after the current frame. Unknown names log `no scene named "…"`. `player.scenes` lists the names and `player.scene` is the current one. Your data carry over to the new scene; Properties start from the new scene's defaults with your data applied on top.

The [React page](./react.mdx#switching-scenes-scene) shows how to keep a `scene` prop in step with scene changes the game makes itself.

## Calling game code: `call`

A game script can offer a function to the page with `ctx.on(name, fn)`. The page calls it with `player.call(name, arg)`, synchronously, and gets its return value.

Toast Catch starts a round on a click or Space. To let the page start one too (from a "Play" button outside the game, say), you would add a function to its script. The safest pattern is for the function to set a flag that the frame loop picks up:

```js title="in the game: additions to Toast Catch"
ctx.on('start', () => { g.wantStart = true })
ctx.on('getScore', () => ctx.props.score)

if (g.mode !== 'play') {
  if (ctx.tap || ctx.keysDown.has('space') || g.wantStart) {
    g.wantStart = false
    start()
  }
} else {
  // ...unchanged
}
```

```js title="on the page"
player.call('start')
const score = player.call('getScore')  // → a number
```

- The function exists only once the script that registers it has run (the first frame its state is active). Calling earlier returns `undefined` and logs ``no script function "start" (register it with ctx.on('start', fn))``.
- Unlike data, `call` is immediate and can return a value, so it's the right tool for "start", "reset", "skip intro", "give me the current score".
- The same functions can be run by a button's On Click "Call script function" action inside the game.

## What the game side looks like

If you also build the game, here is the counterpart of each tool. Full details are in [Properties and data](../scripting/props-and-data.mdx) and [Events and messages](../scripting/events-and-messages.mdx).

```js title="a Code program in the game"
// Data: read what the page sent (read-only; {} in the editor).
const speed = Number(ctx.data.speed) || 1

// Properties: scripts read and write them, bound labels update without
// code, and every change the game makes is reported to the page as 'prop'.
ctx.props.score += 1

// Functions the page can call with player.call(name, arg).
ctx.on('reset', () => { ctx.props.score = 0 })

// Messages to the page: player.on('event') / onEvent.
ctx.emit('gameover', { score: ctx.props.score })
```

Inputs and triggers need no code: they are the state machine's own inputs, set in the state machine editor.

:::tip Test before you embed
In the editor, `ctx.data` is an empty object, so write games that work without data (`Number(ctx.data.speed) || 1`). Give Properties sensible defaults; the embed starts from them until your page sends values.
:::
