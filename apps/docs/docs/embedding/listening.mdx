# Listening to the game

The game talks back in four ways, plus errors:

| Event | Payload | Fires when | React prop |
|---|---|---|---|
| `event` | `{ name, payload }` | a script calls `ctx.emit(name, payload)`, or an On Click "Call script function" names a function no script registered | `onEvent` |
| `prop` | `{ name, value }` | the **game** changed one of its scene Properties | `onPropChange` |
| `state` | `{ layer, state, previous }` | a state machine layer enters a new state | `onStateChange` |
| `scene` | `{ scene, previous }` | the scene switched (by the page or by the game) | `onSceneChange` |
| `error` | `{ error }` | a frame threw (the game keeps running) | `onError` |

```js
player.on('event', ({ name, payload }) => { /* … */ })
player.on('prop',  ({ name, value }) => { /* … */ })
player.on('state', ({ layer, state, previous }) => { /* … */ })
player.on('scene', ({ scene, previous }) => { /* … */ })
player.on('error', ({ error }) => { /* … */ })
```

`on` returns a function that unsubscribes. `off(type, fn)` does the same for a named function. A listener that throws is caught and logged, and the other listeners still run.

Each of these is also dispatched as a bubbling DOM event (`an1:event`, `an1:prop`, …) on the player's container. See [DOM events](#dom-events) below.

## Events: messages on purpose

Events are the game saying something deliberately: "the round ended", "level finished", "the player picked this item". The game's script sends them:

```js title="in the game (Hop)"
ctx.emit('gameover', { score, best: g.best })
```

and your page receives them. Here each finished run of [Hop](../games/hop.mdx) posts a toast notification in the page's own HTML:

```jsx live
function RunToasts() {
  const [toasts, setToasts] = React.useState([])
  const [runs, setRuns] = React.useState(0)
  const notify = (text) => {
    const id = Math.random()
    setToasts((t) => [...t, { id, text }])
    setTimeout(() => setToasts((t) => t.filter((x) => x.id !== id)), 2600)
  }
  return (
    <div style={{ position: 'relative' }}>
      <ToastyPlayer
        game="/games/hop.teab"
        style={{ height: 240 }}
        onEvent={(e) => {
          if (e.name !== 'gameover') return
          setRuns((n) => n + 1)
          const { score, best } = e.payload
          notify(score >= best && score > 0 ? 'New best: ' + score : 'Run over: ' + score + ' (best ' + best + ')')
        }}
      />
      <p>Runs finished: {runs}</p>
      <div aria-live="polite" style={{ position: 'absolute', top: 8, right: 8, display: 'grid', gap: 6 }}>
        {toasts.map((t) => (
          <div key={t.id} style={{ background: '#1f2328', color: '#fff', padding: '6px 10px', borderRadius: 8, fontSize: 13 }}>
            {t.text}
          </div>
        ))}
      </div>
    </div>
  )
}
```

The payload is whatever the script passed (any JSON-like value, or `undefined`). Events are delivered straight away, during the frame that sent them.

### Events from buttons, without code

A UI Button's **On Click** can run a **Call script function** action. If no script registered a function with that name (`ctx.on`) and the game is embedded, the click reaches your page as an `event` with that name, and the action's argument as the payload (parsed as JSON if it is valid JSON, otherwise the raw text). So a designer can wire a "Share score" button to a `share` event with argument `{"channel": "link"}` and never write a script. See [UI components](../components/ui-components.mdx).

When the game runs in the editor rather than embedded, these clicks report a missing function in the Console instead, and `ctx.emit` calls are written to the Console so you can see what the page would receive.

## Property changes

When the game changes one of its scene Properties (a script writes `ctx.props.score`, an On Click action sets a Property, a slider in the HTML UI writes one), you get a `prop` event with the new value. Toast Catch keeps `score` and `lives` as Properties, so the page can mirror them in its own HUD:

```jsx live
function PageHud() {
  const [score, setScore] = React.useState(0)
  const [lives, setLives] = React.useState(3)
  return (
    <div>
      <div style={{ display: 'flex', justifyContent: 'space-between', padding: '8px 12px', border: '1px solid var(--ifm-color-emphasis-300)', borderRadius: 8, marginBottom: 8 }}>
        <span>Score <b>{score}</b></span>
        <span aria-label={lives + ' lives'}>{'♥'.repeat(Math.max(0, lives))}{'♡'.repeat(Math.max(0, 3 - lives))}</span>
      </div>
      <ToastyPlayer
        game="/games/toast-catch.teab"
        style={{ height: 300 }}
        onPropChange={(e) => {
          if (e.name === 'score') setScore(e.value)
          if (e.name === 'lives') setLives(e.value)
        }}
      />
    </div>
  )
}
```

```js
player.on('prop', ({ name, value }) => {
  if (name === 'score') scoreboard.textContent = value
})
```

- Your own `set` / `data` writes are **not** echoed back as `prop` events. Only changes the game made.
- Changes are checked once per frame. If the game changes a Property several times in one frame, you get the final value once. A Property the game writes every frame with the same value (Hop writes `score` every frame) only produces an event when the value actually changes.
- Starting values are not events. Read them with `player.get(name)` when the player is ready.
- Color Properties arrive as `[r, g, b, a]` arrays with channels from 0 to 1.

### Event or Property?

Toast Catch reports the score both ways, which shows the difference:

- The **`score` event** fires once per catch, with the new score. Use events for *moments*: play a sound on the page, count catches, send analytics.
- The **`score` Property** reports every change, including the reset to `0` when a new round starts, which sends no event. Use Properties for *values* the page displays.

## State changes

Every time the state machine enters a state, you hear about it:

```js
player.on('state', ({ layer, state, previous }) => {
  if (layer === null && state === 'Results') showShareButtons()
})
```

- `layer` is `null` for the base layer, or the name of an extra state machine layer. Each layer reports its own changes.
- `previous` is the state it left.
- The starting state is **not** reported as a change. Read `player.state` and `player.layerStates` when the player is ready.

This lets the animation itself carry meaning, with no event code in the game: when the intro reaches `Idle`, enable the Start button; when the boss reaches `Defeated`, show the reward. Toast Catch and Hop keep their modes in a script and stay in a single state, `Play`, so they report their moments with `ctx.emit` instead. For UI animation, state changes are the main signal; Toasty Lite reports them the same way (see [Toasty Lite](../runtimes/lite.mdx)).

## `waitForState`: await a moment

`waitForState(state, layer = null)` returns a promise that resolves the next time the base layer (or the named layer) **enters** `state`, or straight away if it is already in it. It reads well in async code:

```js
await player.waitForState('Idle')       // the intro animation finished
startButton.disabled = false

player.fire('open')
await player.waitForState('Open')       // the door animation reached Open
showMenu()
```

`waitForState` never rejects and has no timeout. If the state might never come (the user leaves, the player is destroyed), race it against your own timeout:

```js
const timeout = new Promise((resolve) => setTimeout(resolve, 5000, 'timeout'))
const result = await Promise.race([player.waitForState('Done').then(() => 'done'), timeout])
```

For script-driven games like the two examples, wrap the event you need in a promise instead:

```js
const nextGameOver = () => new Promise((resolve) => {
  const off = player.on('event', ({ name, payload }) => {
    if (name === 'gameover') { off(); resolve(payload) }
  })
})

const { score } = await nextGameOver()
await saveScore(score)
```

## Scene changes

```js
player.on('scene', ({ scene, previous }) => {
  analytics.track('scene', { scene, from: previous })
})
```

Fires for every switch, whether your page asked for it (`loadScene`, the `scene` prop) or the game did (a script's `ctx.loadScene`, an On Click "Load scene" action). The start scene is announced before `createPlayer` resolves, so `player.on('scene')` won't hear it; read `player.scene` when ready.

## Errors

```js
player.on('error', ({ error }) => reportToSentry(error))
```

A frame that throws is skipped and the next frame runs as usual. To keep the console readable the player reports the first three errors and then one in every 600. In React, `onError` receives both these and loading errors (bad URL, broken file). With plain JS, loading errors reject the `createPlayer` promise instead.

## The `ready` event

`ready` (`{ scenes, scene }`) is dispatched *before* `createPlayer` resolves, so subscribing with `player.on('ready', …)` is too late to hear it. Use the resolved player (or React's `onReady`, or the `<an1-player>` element's `an1:ready`). If you need it as a DOM event, add the listener to the container itself (it doesn't bubble) before calling `createPlayer`:

```js
box.addEventListener('an1:ready', (e) => console.log('scenes', e.detail.scenes), { once: true })
const player = await createPlayer(box, { game: '/an1mbyt3/game.teab' })
```

## DOM events

Every event above is also dispatched as a DOM `CustomEvent` named `an1:<type>` on the player's container, with the payload as `detail`. These events **bubble** (all except `an1:ready`), so code that doesn't hold the player object can listen on any ancestor, even `document`:

```js
// Anywhere on the page: an analytics module, a leaderboard widget.
document.addEventListener('an1:event', (e) => {
  const { name, payload } = e.detail
  if (name === 'gameover') analytics.track('game_over', payload)
})
```

For the `<an1-player>` element, the container is the element's inner box, so the events bubble through the element itself. See [The an1-player element](./custom-element.mdx#events).

## What the game side looks like

```js title="in the game"
ctx.emit('levelDone', { level: 3, stars: 2 })  // → 'event'
ctx.props.score = 1200                          // → 'prop'
ctx.loadScene('Results')                        // → 'scene'
// state changes need no code: the state machine reports them
```
