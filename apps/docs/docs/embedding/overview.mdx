# Embedding the Toasty engine

## Lite or engine?

Toasty has two web runtimes. Pick the one that matches what you are putting on the page.

| | [Toasty Lite](../runtimes/lite.mdx) | Engine embed (this section) |
|---|---|---|
| Made for | UI animation: icons, buttons, toggles, loaders, illustrations | Games and anything scripted |
| Size | About 25 KB of JavaScript | About 25 MB of WebAssembly, plus about 230 KB of JavaScript |
| Per page | Any number | One |
| Scripts, physics, particles, images, audio, 3D, post effects | No | Yes |
| State machines, Properties, bindings, pointer interaction | Yes | Yes |
| Files | A `.json` from Export → Animation → Toasty Lite | A `.teab` from Export → Game → Website embed |

If the thing on your page is a like button, a menu icon or a progress ring, use Lite: it starts instantly and you can have dozens. Use the engine for a game, or for a scene that needs a script. [Lite vs engine](../runtimes/lite-vs-engine.mdx) compares them feature by feature.

## What the engine embed is

The engine embed runs a Toasty game **inside your own page** and lets your code steer it. It is not a video and not an iframe. It is the same engine the editor runs in Playground, drawing into a canvas in a box you choose, and your page can talk to it while it plays.

Click the game to start it, catch a few slices, and watch the page update.

```jsx live
function FirstLook() {
  const [speed, setSpeed] = React.useState(1)
  const [score, setScore] = React.useState(0)
  const [last, setLast] = React.useState(null)
  return (
    <div>
      <ToastyPlayer
        game="/games/toast-catch.teab"
        data={{ speed }}
        style={{ height: 300 }}
        onEvent={(e) => {
          if (e.name === 'score') setScore(e.payload.score)
          if (e.name === 'gameover') setLast(e.payload.score)
        }}
      />
      <p style={{ display: 'flex', gap: 16, flexWrap: 'wrap', alignItems: 'center' }}>
        <span>Score from the game: <b>{score}</b></span>
        {last !== null && <span>Last round: <b>{last}</b></span>}
        <label>
          Speed{' '}
          <input type="range" min="0.5" max="2" step="0.1" value={speed}
            onChange={(e) => setSpeed(Number(e.target.value))} /> {speed.toFixed(1)}×
        </label>
      </p>
    </div>
  )
}
```

Edit the code and the example re-runs. Two things happen there:

- **The page sends data in.** `data={{ speed }}` reaches the game's script as `ctx.data.speed`. Drag the slider mid-round and the toast falls faster.
- **The game sends events out.** The script calls `ctx.emit('score', { score })` on every catch and `ctx.emit('gameover', { score })` at the end of a round, and `onEvent` receives them.

That two-way link is what this section is about. Toast Catch and the other example game, Hop, are explained line by line in [Games](../games/index.mdx).

## The three ways to embed

All three wrap the same player and have the same capabilities. Pick the one that matches your site.

| You have | Use | Read |
|---|---|---|
| A React app (Vite, Remix, Next.js) | `<An1Player>` from `an1mbyt3-react.js`. Props steer the game live. | [React](./react.mdx), [Next.js](./nextjs.mdx) |
| Any page with JavaScript (Vue, Svelte, Angular, plain HTML) | `createPlayer(element, options)` from `an1mbyt3-embed.js`. Returns a player object. | [Plain JavaScript](./vanilla-js.mdx) |
| HTML you can't script much (a CMS, a static site) | The `<an1-player>` tag, registered with `defineAn1PlayerElement()`. | [Custom element](./custom-element.mdx) |

## How the page and the game talk

```text
             your page                                         the Toasty game
 ┌─────────────────────────────────┐                 ┌───────────────────────────────────┐
 │ player.set('speed', 1.5)        │ ─── data ─────▶ │ ctx.data.speed (+ Property "speed"│
 │                                 │                 │   if the scene has one)           │
 │ player.setInput('paused', true) │ ─── inputs ───▶ │ state machine inputs              │
 │ player.fire('restart')          │ ─── triggers ─▶ │ state machine triggers            │
 │ player.loadScene('Level 2')     │ ─── scenes ───▶ │ scene switch                      │
 │ player.call('start', arg)       │ ─── calls ────▶ │ ctx.on('start', fn)               │
 │                                 │                 │                                   │
 │ on('event') ◀── ctx.emit('gameover', { score }) ──│ scripts, On Click actions         │
 │ on('prop')  ◀── "Property lives is now 2" ────────│ scene Properties                  │
 │ on('state') ◀── "entered state Paused" ───────────│ state machine                     │
 │ on('scene') ◀── "switched to Level 2" ────────────│ scene switches                    │
 └─────────────────────────────────┘                 └───────────────────────────────────┘
```

**Into the game:**

- **Data** is for *values*: a difficulty, a player name, a colour. Each value reaches `ctx.data` for scripts, and the scene **Property** with the same name if there is one (so text or colours bound to that Property update with no code). See [Sending data in](./data-binding.mdx).
- **Inputs and triggers** drive the scene's [state machine](../editor/state-machines.mdx): a Bool, Number or Enum input changes which state it is in; a Trigger is a one-shot "do this now".
- **Scenes** can be switched from the page, and **functions** a script registered with `ctx.on` can be called.

**Out of the game:**

- **Events** are messages the game sends on purpose with `ctx.emit(name, payload)`, or from a button's On Click "Call script function" action.
- **Property changes** tell you when the game changed one of its scene Properties. Toast Catch keeps `score` and `lives` in Properties, so the page can show them in its own HTML.
- **State changes** tell you every time the state machine enters a state.

See [Listening to the game](./listening.mdx).

## What ships

You don't install an npm package. **Export → Game → Website embed (React / JS)** in the editor writes a folder with:

- three prebuilt JavaScript files you import from your code (`an1mbyt3-embed.js`, `an1mbyt3-react.js`, `an1mbyt3-engine.js`) plus TypeScript declarations;
- two static files your site serves: `game.teab` (your game) and `an1mbyt3_wasm_bg.wasm` (the engine, about 25 MB uncompressed, much smaller gzipped);
- a README, a step-by-step GUIDE, an AGENTS.md for AI coding assistants, a machine-readable `an1mbyt3.json` describing your game's Properties, inputs, data keys and events, and a working `example.html`.

[Exporting for the web](./export-for-web.mdx) walks through it.

## Things to know up front

:::caution One player per page
Only one engine player runs on a page at a time. Creating a second one destroys the first (the engine's HTML overlay, scene Properties and script state are page-wide). Put the game on the page with the engine, and build the animated UI around it with [Toasty Lite](../runtimes/lite.mdx), which has no such limit. The live examples in these docs follow the same rule: starting one puts the previous one back to its poster.
:::

:::note Give the box a height
The game fits inside its container like a video (letterboxed). An empty `div` is 0 px tall, so you would see nothing. Always give the container a height.
:::

:::tip Build it first, embed it second
The embedded player runs the same engine as the editor's Playground, so a game behaves exactly as it does when you press Play. When the game is not embedded, every `ctx.emit` is written to the editor's Console instead (for example `ctx.emit("gameover", {"score":12}) — reaches the page when this game is embedded`), so you can finish and test the game before you write any website code.
:::
